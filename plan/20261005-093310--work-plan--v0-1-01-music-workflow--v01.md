## Confirmed baseline and assumptions

The application is a Windows desktop application using Python, Tk, NumPy, an existing native C++ spectrum backend, FFmpeg decoding, SoundCard capture, and a CPU portable AI runtime. Its current automated tests use Python unittest and include hidden real Tk widgets, native parity checks, and frozen application diagnostics. The previous release had 316 passing tests. Those numbers describe the old build and must not be reused as evidence for the new one. The current repository starts clean and contains the released v0.0.13 implementation and documentation.

The current chord chart shows sixteen bars per page with four bars in each row. Its bar grid is manually adjustable using a constant BPM, beats per bar, and first-bar offset. These settings are not a downbeat transcription model. Original detected events may fall across bars and must remain intact. Chord candidates and guitar shapes are theoretical suggestions. The original-mix fallback deliberately avoids claiming guitar-specific fingering or bass inversion. Preserve those safeguards throughout playback, editing, and export.

The current stem removal function writes a mixed WAV excluding selected instruments. It does not provide a retained editable set of all stems or an in-app playback mixer. The model cache is shared and may require an initial download. The first implementation should reuse existing dependencies when they can satisfy the behavior safely. Use bounded file-backed audio rather than decoding an entire twenty-minute six-stem session into an unbounded memory structure. Treat local media and temporary analysis artifacts as private. Do not include the user's sample audio or model cache in Git or release archives.

Use source-relative and original-file time deliberately. Playback begins at the analysis selection start and exposes position relative to that selection, while the existing displayed source timestamps may include an offset. A click on a bar should seek to the appropriate selection-relative position, including any introductory section before the first full bar. A long event that continues across a bar must not acquire a duplicate editable identity. The audio file may have moved or disappeared after analysis; handle that state as a recoverable missing-source error rather than reusing unrelated audio.

## Delivery sequence

### First slice: controlled audio playback

Introduce playback as a small, testable service with explicit preparation, ready, playing, paused, stopped, finished, cancelled, and failed states as needed by the actual UI. Do not start audible playback on file selection, analysis completion, chart rendering, language change, or application startup. Require a deliberate playback action. Supply play and pause, stop, position seeking, and a loop for a selected bar or range. Keep output gain conservatively bounded and communicate that the output uses the configured Windows playback route. Report a missing output device without crashing the UI or discarding the analysis result.

Decode supported input media into managed temporary PCM using the same trusted FFmpeg distribution and range limits as the existing application. Never alter the user's source file. Keep decoding and audio output away from Tk's main thread. Only the main thread may change widgets. Make cancellation and close cleanup deterministic, and reject stale preparation completions after a new source is selected. Do not block the user interface while waiting for a device or large decode. Stop playback before mutually exclusive capture, AI processing, language rebuild, or application shutdown until evidence shows a safe combined operation.

Drive the displayed playhead from processed audio frames or a bounded playback-clock model rather than unrelated elapsed wall time. Be explicit that shared-mode audio buffering can introduce small latency; do not describe this as sample-accurate DAW transport. Keep seeking and loop bounds inside the actual decoded duration, handle end-of-file without spinning or sending invalid buffers, and avoid an audible replay after stop. Tests should use deterministic output doubles for state and threading behavior, with real decoded PCM for file boundaries. A hidden widget test should prove that existing chart pages survive integration and that selected or currently playing bars can be identified without deleting chord labels or their evidence.

### Second slice: editable chords with preserved provenance

Add a focused correction workflow after playback is functional. Let the user select a detected event, choose a supported chord name or mark it unknown, apply the change, and undo or restore the original estimate. Keep the original analysis evidence unchanged. Store corrections separately and label corrected events as user edits. Editing a displayed continuation should update the underlying event consistently everywhere it appears. Do not invent a high machine-confidence score for a user-entered chord, and do not retain stale detected shapes, bass claims, or pitches after the symbol changes.

Preserve corrections across page navigation, manual bar-grid changes, and language switching. Include them in the existing saved analysis data and readable exports. A controlled way to reopen those results may be added only as the persistence support necessary for this editing workflow, not as a general multitrack project format. Validate imported data before treating it as a playback request. A saved path is provenance, not permission to run code or access a remote resource. Do not execute serialized objects. Ensure malformed corrections, invalid indices, huge input collections, non-finite times, and unsupported symbols fail safely without mutating the previous valid result.

Keep generated guitar diagrams theoretical and retain the full-mix source guard. A manual chord name alone cannot establish what the original guitarist played. Editing does not change the tone recipe, separated audio, reference spectrum, or underlying acoustic analysis. Make the distinction visible in both Korean and English. Verify editing at a page boundary, an unknown section, a long sustained chord, and a result with an analysis-start offset. Save and reopen a synthetic corrected result to prove the persistence contract without distributing user media.

### Third slice: per-instrument mixing and independent audio export

Extend the existing separation workflow to retain the six estimated parts for a bounded session: vocals, drums, bass, guitar, piano, and other. Offer clearly labeled gain controls and solo and mute behavior. Define their interaction consistently: a muted part remains silent, and when any eligible solo is active only the selected eligible solo parts sound. Silence caused by the user's choices is legitimate and should not be confused with a failed separation. Keep the original input available as a clearly separate comparison source. The piano part is not a guaranteed detector for every synthesizer or keyboard.

Perform one separation per selected input range and reuse the resulting stems for adjustments and export. Do not rerun the model for every fader movement. Keep all stems frame-aligned and apply one explicit anti-clipping policy when producing the final mix. Avoid independent per-stem loudness normalization that changes their relative balance without consent. Allow individual WAV exports and a mixed WAV export to new user-chosen destinations. Do not overwrite the source, existing destinations, or a file that appears while an export is in progress. Remove incomplete outputs after cancellation or failure and make all-or-nothing expectations clear when exporting multiple files.

Provide real preparation and inference progress. Reuse the existing cancellation, model-download errors, device resolution, and offline-cache behavior. Require confirmation or a safe non-destructive choice when abandoning an active separation or replacing the current stem session. Manage temporary storage ownership narrowly and clean only files created by the application. A restart need not resume a partly completed inference; document that limitation instead of implying checkpoints exist. Test full and partial final chunks, stereo and mono inputs, finite samples, unequal frame counts, no selection, cancellation, device failure, and destination races.

### Separation-quality work within the mixer slice

Compare the current extraction path against a bounded higher-quality inference option where the current model supports it. Inspect the actual installed model API and current primary documentation before choosing overlap or repeated-shift settings. Pay special attention to chunk boundaries, fade and overlap behavior, and reconstruction consistency. Prefer improvements that preserve timing and avoid discontinuities over unmeasured model replacement. Keep an explicit speed versus quality setting if a more expensive path is useful; do not silently make every analysis much slower.

Use known synthetic component mixtures to test plumbing, sample alignment, boundary continuity, reconstruction, and gain behavior. These checks are not proof of general real-song source-separation accuracy. For any genuine quality claim, use legally available independent reference stems and define metrics and comparison conditions before interpreting results. The user's Room 335 file is suitable for end-to-end regression and a listening comparison, but without reference stems it cannot establish a numeric separation accuracy. If listening or independent references remain unavailable, report the implemented algorithmic change and the unverified perceptual benefit separately. Do not publish “more accurate” simply because a quality preset uses more compute.

### Fourth slice: sixteen-bar PDF and printing

Export the same effective chart shown in the application, including corrections, manual bar-grid settings, source labels, and unknown regions. Produce readable A4 pages with four bars per row and sixteen bars per musical page whenever the content fits. Never discard extra changes in a dense bar merely to maintain a rigid drawing. Use clearly labeled continuation or supplemental detail pages when needed and preserve every event in the document. Keep song title, page number, tempo, meter, offsets, and manual-correction legend legible. Do not copy lyrics, artwork, or capo values from the user's layout reference.

Use a well-supported PDF library only after checking distribution and font requirements. Korean and English text must render with available, legally distributable fonts; avoid relying on a developer-only font directory. Standard-tuning diagrams should be drawn as vector lines and symbols where practical. Prevent file overwrite without the existing save dialog's explicit user choice, and use a temporary-file commit so a failed render does not leave a success-looking document. Printing should give the user a preview or open the saved PDF in their PDF application's print workflow. Do not silently send a job to a physical printer. Test the workflow independently of whether this machine has a printer installed.

Render representative exported PDF pages to images and inspect layout, typography, clipping, unknown labels, diagrams, and multi-page ordering. Also inspect document text and page count, but do not treat text extraction as a substitute for visual review. Include short and long charts, empty or unknown spans, dense bars, both languages, edited symbols, nonzero source offset, and the final partially filled page. Distinguish automated PDF checks from physical print testing. Do not distribute any private audio or source path through PDF metadata without an intentional user choice.

## Architecture and optimization boundaries

Keep the existing desktop architecture and native spectrum engine. Separate audio transport, correction data, stem-session storage and mix/export, and chart document rendering into cohesive modules with small interfaces. Avoid a generic plugin system, broad application rewrite, or unrelated cleanup. The UI integration may evolve in small sections but should retain the existing input, recipe, theory dictionary, diagnostics, and reference comparison behavior. Prefer the standard library and the project's already installed dependencies. Evaluate a small PDF dependency and any genuinely necessary playback dependency explicitly before freezing a new build.

Measure the operation that could benefit from C++, using the same input sizes and conditions for reference and candidate implementations. NumPy and the AI runtime already execute substantial native work; replacing a Python call site alone is not evidence of a speedup. If the actual bottleneck is model inference, device buffering, disk decoding, or PDF rendering, improve that path rather than introducing native code elsewhere. A C++ change must preserve the current ABI contract or deliberately version it, retain a tested fallback, and include parity, memory-safety, boundary, and final-package checks. Report measured scope and hardware rather than general speed claims.
