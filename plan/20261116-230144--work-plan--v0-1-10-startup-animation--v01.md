## Presentation and behavior contract

Reuse the existing Tkinter stack and the application's dark navy, pale text and mint accent colors. Draw a small procedural waveform with a fixed number of Canvas items rather than loading a video, GIF, remote image or new graphics dependency. The brand name is the visual focus; the waveform communicates startup activity and is decorative rather than a representation of recorded audio. Do not capture audio, query devices, invoke the chord engine or create network traffic to drive it. Keep the waveform bounded in size and update rate so its memory and CPU requirements are predictable. Update existing Canvas items instead of creating new items every frame. Use the event loop's scheduled callbacks; never block with sleep or busy waiting.

Keep English branding in Arial Narrow and Korean status and controls in Malgun Gothic, with English status and controls in Arial Narrow. Read the existing language setting defensively using the bounded settings read already used for startup. Missing, malformed or oversized settings fall back to Korean without preventing launch. The animation must coexist with the current progress text and real determinate download and verification progress. Decorative movement must not pretend that a startup percentage is known. No arbitrary percentage should be shown for import or application initialization. Avoid flashing, whole-window opacity effects, external effects lists, or an unrelated startup settings page.

Allow a brief approximately 700 millisecond intro when no update is needed, with an immediate continue button. The update check starts immediately and overlaps the intro. Once update checking has occupied that interval, opening the current application must not add another delay. A successful update handoff, a close request or an explicit continue action must not wait for the decorative duration. Do not add an animation to both sides of the same view-to-main transition. An automatically updated executable may display its own short normal startup surface while still honoring its skip-update flag, but it must not begin another update check.

Separate the decision to show a startup surface from the decision to perform a portable update. Normal frozen Windows launches can show the animation, including Store-packaged installations, unknown package-identity results and skip-update execution. Only the existing explicitly unpackaged update policy may start portable update work. Source execution may continue to bypass this executable-specific intro. Diagnostic command-line paths and frozen multiprocessing dispatch must remain ahead of any window or startup-view construction. Preserve the offline fallback and inherited original data directory used by a verified portable update. Do not widen the trust boundary around update selection, archive validation, executable launching, or Store data locations.

## Implementation sequence and lifecycle

Start by testing the startup transition through inert fake roots and views. The missing behaviors should be observable without any Tk window: a short animation-only path exists, a close request exits, an explicit continue skips the wait, a disabled update policy never constructs an update worker, and teardown leaves no owned timers or root bindings. Keep the existing updater controller as the boundary between network/archive work and the main GUI thread. Its queues and cancellation precedence already have meaningful tests and should remain intact unless an integration regression demonstrates a narrow required repair.

Keep Tk construction, waveform drawing, scheduling, status rendering and main application construction on the main thread. Continue using the existing daemon updater worker for network and archive activity. Maintain one Tk root. Avoid an unnecessary general animation engine or event-bus framework. A small view responsible for its own waveform timer and a startup runner responsible for transition timers are sufficient. Keep pure waveform geometry separate enough to verify finite coordinates, a fixed shape count and bounded amplitude with deterministic elapsed times, but do not add a standalone configurable rendering system.

Every scheduled callback must have a clear owner and lifetime. Store the handles for waveform updates, update polling and the remaining intro duration. Cancel owned callbacks before destroying their widgets. A callback retained by a fake scheduler and invoked after teardown must perform no widget operations and must not schedule another callback. Completion and destruction must be idempotent. Capture the root's prior close protocol and restore it when the startup surface yields control; the main application subsequently installs its own close handler. Any additional keyboard binding must be removed precisely without disturbing unrelated handlers. Prefer the existing button and native close control if an extra binding would add unnecessary state.

Distinguish update completion from overall startup completion. An already completed update check may be waiting for the brief presentation interval, but close and explicit continue must still take effect immediately. They must not be ignored because the updater controller has already set its own finished state. A queued update result must never launch after cancellation. Handoff success must exit without constructing the old main application. Handoff failure must retain the current application fallback. Animation-only paths must not accidentally instantiate network work just to reuse a controller. If animation rendering encounters a Tk drawing failure, stop decorative updates and preserve the static startup controls and normal continuation when possible; do not turn an optional visual effect into a permanent launch blocker.
